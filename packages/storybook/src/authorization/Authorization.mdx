# Authorization

Control UI visibility from a server-derived access decision, without adding wrapper elements.
Server endpoints must enforce permissions independently.

## Page states

Page fallbacks use the shared `StatusState` presentation for loading, guidance, and errors.

## Setup

Mount one `AuthorizationProvider` in the app or layout. Descendants share its controller through
[Svelte context](https://svelte.dev/docs/svelte/context).

Create the controller with `createAuthorizationController`. Set `initialStatus` from the server decision;
it defaults to `pending`. Apply later decisions with `resolve(status)`. Keep SSR instances request-local
to isolate users.

```svelte
<script lang="ts">
  import type { Snippet } from "svelte";

  import type { AuthorizationController } from "@a-novel-kit/uikit";
  import { AuthorizationProvider } from "@a-novel-kit/uikit";

  let { authorization, children }: { authorization: AuthorizationController; children: Snippet } = $props();
</script>

<AuthorizationProvider controller={authorization}>
  {@render children()}
</AuthorizationProvider>
```

The provider renders all children; visibility belongs to the boundaries below.
Replacing its controller updates existing consumers.

## Usage

### Render conditional content

`AuthorizationBoundary` inherits the nearest controller. It renders children for `allowed`,
or `fallback(status)` otherwise. Without a fallback, the region disappears.

```svelte
<script lang="ts">
  import { AuthorizationBoundary, Button } from "@a-novel-kit/uikit";
</script>

<AuthorizationBoundary>
  <Button>Edit document</Button>
</AuthorizationBoundary>
```

Page fallbacks distinguish an unfinished check (`pending`), a missing session (`anonymous`),
denied permission (`forbidden`), and a failed check (`unavailable`). The application handles login,
HTTP 403, retry, and accessible feedback; an outage should not send the user to login.

### Read the decision with the hook

Use `useAuthorization()` for custom presentation, such as disabling a control. Call it during component
initialization and read state reactively:

```svelte
<script lang="ts">
  import { Button, useAuthorization } from "@a-novel-kit/uikit";

  const authorization = useAuthorization();
  const canEdit = $derived(authorization.state.status === "allowed");
</script>

<Button disabled={!canEdit}>Edit document</Button>
```

Both consumers throw when context is missing, unless the boundary receives an explicit controller.

## Local overrides

Pass `controller` to a boundary for resource-specific permissions or an isolated story/test.
Its descendants, including the fallback, inherit that decision; siblings keep the app decision.

An override replaces the inherited decision. Include all required permissions when computing it.
These stories use fixed controllers to keep review states stable.
